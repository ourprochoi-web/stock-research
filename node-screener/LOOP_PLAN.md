# 루프 기반 개발 계획서 v2

> 불가결 노드 스크리너 — 모든 Phase에 자기교정 루프 내장
> 작성일: 2026-07-25

---

## 전체 루프 아키텍처

```
Phase 0 ──→ [L0 스키마 스트레스] ──→ Gate 0 (왕복 + 엣지케이스 통과)
                                       │
Phase 1 ──→ [L1 추출 품질] ←→ [L2 커버리지 갭] ──→ Gate 1
                                       │
Phase 2 ──→ [L3 그래프 무결성] → [L4 정답지 캘리브레이션] ──→ Gate 2
                                       │
            [L5 데이터 품질] ←→ [L6 강건성] ──→ Gate 3
                                       │
Phase 3 ──→ [L7 시각화 QA] ──→ Gate 4 (최종)
```

핵심 원칙: **모든 Phase에 자기교정 루프 내장. 원샷 실행 금지.**

---

## 루프 간 연동 흐름

```
L1 추출 품질 ←── 프롬프트 피드백 ──→ L5 데이터 품질
     │                                    │
     ↓                                    ↓
L2 커버리지 갭 ──→ L3 그래프 무결성 ──→ L4 정답지 캘리브
     │                                    │
     └──── CSV 수동 보강 ←────────────────┘
                                          │
                                     L6 강건성
```

**핵심**: L5에서 체계적 오류 패턴 발견 → L1 프롬프트 수정으로 역류. L4에서 엣지 누락 진단 → L3로 회귀. 루프가 독립이 아니라 **상호 피드백**.

## L0 — 스키마 스트레스 루프 (Phase 0)

| 항목 | 내용 |
|------|------|
| 입력 | models.py, graph_io.py |
| 사이클 | 왕복 테스트 → 엣지케이스 주입 (빈 evidence, alias 역직렬화, 한글 ID, 중복 엣지) → 실패 패턴 수집 → 스키마/IO 수정 → 재테스트 |
| 지표 | 테스트 통과율 |
| 종료 | 전체 테스트 통과 + 엣지케이스 0 실패 |
| 최대 | 3 사이클 |

---

## L1 — 추출 품질 루프 (Phase 1 핵심)

| 항목 | 내용 |
|------|------|
| 입력 | seed/recent/*.md 13개 파일 |
| 사이클 | LLM 추출 → Pass 2 인용구 검증 → **폐기율 분석** (파일별·유형별) → 폐기 원인 분류 (환각/오인용/범위초과/형식오류) → **프롬프트 규칙 추가/수정** → 재추출 (폐기율 높은 파일만) |
| 지표 | Pass 2 통과율 (전체 + 파일별), 폐기 유형 분포 |
| 종료 | 전체 통과율 ≥ 85% AND 단일 파일 통과율 ≥ 70% |
| 최대 | 3 사이클 (프롬프트 개선 3회) |
| 실패 시 | 통과율 미달 파일의 폐기 트리플 목록 + 원인 보고 → 수동 보강 판단 |

**L1이 가장 중요한 루프** — 프롬프트 엔지니어링의 피드백 루프.

---

## L2 — 커버리지 갭 루프 (Phase 1, L1과 교차)

| 항목 | 내용 |
|------|------|
| 입력 | 추출 결과 그래프 + ground_truth.yaml 10개 노드 |
| 사이클 | ground truth 노드 존재 확인 → 누락 노드 식별 → 원인 진단 (소스에 없음? 추출 실패? Pass 2 폐기?) → 수동 CSV 보강 or 프롬프트 수정 후 L1 재실행 → 재확인 |
| 지표 | ground truth 커버리지 (10개 중 N개) |
| 종료 | 8/10 이상 포함 (허용 미달 2개는 수동 보강 후보 보고) |
| 최대 | 2 사이클 |
| L1 연동 | 커버리지 실패가 추출 문제면 L1 프롬프트 수정 → L1 재실행 |

---

## L3 — 그래프 무결성 루프 (Phase 1→2 브릿지)

| 항목 | 내용 |
|------|------|
| 입력 | 완성된 그래프 스냅샷 |
| 사이클 | 구조 검사 (고립 노드, 기능 미매핑 기업, 단방향 엣지만 있는 노드) → 이상 목록 → CSV 보강 or 재추출 → 재검사 |
| 지표 | 고립 노드 수, 기능 미매핑 기업 수, 연결 컴포넌트 수 |
| 종료 | 고립 기업 0개, 모든 기업 ≥1 기능 매핑, 체인당 1개 연결 컴포넌트 |
| 최대 | 2 사이클 |

---

## L4 — 정답지 캘리브레이션 루프 (Phase 2)

| 항목 | 내용 |
|------|------|
| 입력 | 그래프 + weights.yaml + ground_truth.yaml |
| 사이클 | 5축 스코어 산출 → Recall@20% + 평균 랭크 백분위 → **미달 원인 이분법 (가중치 문제 vs 엣지 누락)** → 가중치면 weights.yaml 수정, 엣지면 L3로 회귀 → leave-one-out 교차 검증 → 재채점 |
| 지표 | Recall@20%, 평균 랭크 백분위, LOO 통과율 |
| 종료 | Recall ≥ 0.8 AND LOO 전원 상위 30% OR 5사이클 OR 2사이클 연속 정체 |
| 최대 | 5 사이클 |
| 정체 시 | "데이터 보강 필요 노드 목록" + "가중치 한계 분석" 보고 |

---

## L5 — 데이터 품질 루프 (Phase 2-3)

| 항목 | 내용 |
|------|------|
| 사이클 | 엣지 20개 무작위 샘플 → evidence 원문 대조 → 불량 분류 (출처소실/과장/오추출/날짜경과) → 불량 엣지 수정 or 폐기 → **불량 패턴이 체계적이면 L1 프롬프트에 규칙 추가 후 해당 파일 재추출** |
| 지표 | 불량률, 불량 유형 분포 |
| 종료 | 불량률 < 10% |
| 최대 | 3 사이클 |
| L1 연동 | 체계적 오류 패턴 발견 시 L1 프롬프트 수정 → 해당 소스 재추출 |

---

## L6 — 강건성 루프 (Phase 2-3)

| 항목 | 내용 |
|------|------|
| 사이클 | confidence 하위 엣지 10%씩 제거 → 상위 랭킹 유지율 측정 → 랭킹 변동이 큰 노드 식별 → 해당 노드의 고신뢰 evidence 보강 → 재측정 |
| 지표 | 상위 10 랭킹 유지율 (Kendall τ) |
| 종료 | 하위 20% 엣지 제거 시 τ ≥ 0.8 |
| 최대 | 3 사이클 |

---

## L7 — 시각화 QA 루프 (Phase 3)

| 항목 | 내용 |
|------|------|
| 사이클 | 렌더링 → 체크리스트 검증 (그래프 뷰 노드 크기, 점선 엣지, 제거 시뮬, 스코어보드 드릴다운, 2×2 사분면 정확성) → 실패 항목 수정 → 재렌더링 |
| 종료 | 체크리스트 전항목 통과 |
| 최대 | 3 사이클 |

## 실행 프롬프트

### P-0: Phase 0 킥오프 + L0 스키마 스트레스

```
node-screener/spec-node-screener.md를 정독하고 Phase 0을 구현해줘.

구현 후 L0 스키마 스트레스 루프 실행:
1. 기본 왕복 테스트 (저장 → 로드 → 일치)
2. 엣지케이스 테스트 추가 실행:
   - 빈 그래프 (노드 0, 엣지 0)
   - evidence 없는 Edge 생성 시도 → 유효성 에러 확인
   - from/to alias가 JSON 직렬화·역직렬화 양방향 보존
   - 한글 ID + 특수문자 (co_SK하이닉스) 왕복
   - 동일 그래프 2회 저장 → 파일 내용 바이트 일치 (결정론적)
3. 실패 시: 스키마/IO 수정 → 재테스트 (최대 3사이클)
4. 전체 통과 시 Gate 0 증적을 PROGRESS.md에 기록

규칙:
- §3.2 스키마가 단일 소스. 필드 추가/변경 시 DECISIONS.md 기록
- Python 3.9 호환 (Optional[] 사용, X|Y 금지)
```

### P-1: Phase 1 인제스트 + L1 추출 품질 루프

```
Phase 1 시드 인제스트를 구현하고 L1 추출 품질 루프를 실행해줘.

구현:
- src/ingest.py: §5 LLM 2-pass 파이프라인
- src/merge.py: 엔티티 중복 제거
- src/report.py: 통계 리포트

L1 루프 (최대 3사이클):
사이클 N:
1. data/seed/recent/ 13개 파일 인제스트 실행
2. 측정: Pass 2 통과율 (전체 + 파일별)
3. 폐기 트리플 원인 분류:
   - 환각 (원문에 없는 주장)
   - 오인용 (인용구가 다른 맥락)
   - 범위초과 (추론한 관계)
   - 형식오류 (JSON 파싱 실패)
4. 통과율 < 85% OR 단일 파일 < 70%이면:
   - 상위 폐기 원인에 대응하는 프롬프트 규칙 추가
   - 폐기율 높은 파일만 재추출
   - 사이클 N+1로
5. 통과율 충족 시 루프 종료

종료 후 보고:
- 사이클별 통과율 추이 표
- 최종 프롬프트 (어떤 규칙이 추가되었는지)
- 파일별 폐기 상세 (폐기된 트리플 + 사유)
- PROGRESS.md에 L1 증적 기록
```

### P-2: L2 커버리지 갭 루프

```
L1 완료 후 L2 커버리지 갭 루프를 실행해줘.

입력: 추출된 그래프 + data/ground_truth.yaml (10개 노드)

사이클 (최대 2회):
1. ground_truth.yaml의 10개 노드가 그래프에 존재하는지 확인
   - id 매칭 + 이름 유사도 매칭 (정규화 후)
2. 누락 노드별 원인 진단:
   a) 소스 파일에 해당 정보 자체가 없음 → "수동 보강 필요" 판정
   b) 소스에는 있지만 LLM이 추출 실패 → 프롬프트 힌트 추가 후 L1 재실행
   c) 추출했지만 Pass 2에서 폐기 → 인용구 확인, threshold 조정 검토
3. (b) 또는 (c)면 해당 파일 재추출 → 커버리지 재확인
4. (a)면 수동 CSV 보강 후보로 분류

종료: 8/10 이상 커버 OR 미달 노드 전원이 (a) 유형

보고:
- 10개 노드 × {존재/누락/원인유형} 매트릭스
- 수동 보강 필요 노드 목록 + 어떤 데이터가 필요한지
- PROGRESS.md에 L2 증적 기록
```

### P-3: L3 그래프 무결성 루프

```
L2 완료 후 L3 그래프 무결성 루프를 실행해줘.

검사 항목 (체인별):
1. 고립 기업 노드 (엣지 0개)
2. 기능 미매핑 기업 (functions 빈 배열)
3. 연결 컴포넌트 수 (체인당 1개여야 정상)
4. 엣지의 from/to가 존재하지 않는 노드를 참조
5. 같은 기업이 같은 기능에 중복 매핑

사이클 (최대 2회):
1. 검사 실행 → 이상 목록 출력
2. 자동 수정 가능한 것 (중복 제거, 댕글링 참조) → 즉시 수정
3. 수동 판단 필요 (고립 노드 — 삭제 vs 엣지 추가) → 목록 제시
4. 수정 후 재검사

종료: 항목 1-4 전수 통과

보고:
- 체인별 노드/엣지/컴포넌트 통계
- 수정 내역 (자동 + 수동)
- Phase 1 최종 그래프 통계:
  · 체인별 Function/Company/Edge 수
  · confidence 분포 (high≥0.8 / medium 0.5~0.8 / low<0.5)
  · evidence 커버리지 (evidence 있는 엣지 비율)
- PROGRESS.md에 Phase 1 최종 Gate 증적 기록
```

### P-4: Phase 2 스코어링 + L4 정답지 캘리브레이션 루프

```
Phase 2 스코어링을 구현하고 L4 정답지 캘리브레이션 루프를 실행해줘.

구현: §4의 5축 스코어링 + RaRR
- S1~S5 각 축 함수 구현 (NetworkX 활용)
- config/weights.yaml에서 가중치 로드
- 합성 스코어 산출 → 0~100 클립

L4 루프 (최대 5사이클):
사이클 N:
1. 전체 노드 스코어 산출 → 랭킹
2. 채점:
   - Recall@20%: ground_truth 10개 중 상위 20%에 몇 개?
   - 평균 랭크 백분위: ground_truth 노드의 평균 순위
3. Recall < 0.8이면 원인 이분법:
   - [가중치 문제] ground_truth 노드가 그래프에 있고 엣지도 충분하지만 스코어 낮음
     → weights.yaml 조정 (어떤 축을 올리면 해결되는지 분석)
   - [엣지 누락] ground_truth 노드의 betweenness가 낮은 이유가 엣지 부족
     → L3로 회귀하여 엣지 보강 후 재실행
4. leave-one-out 교차 검증:
   - 정답 1개씩 빼고 나머지 9개로 튜닝한 가중치로 빠진 1개 검증
   - LOO 실패 → 가중치가 아니라 데이터(엣지) 보강으로 해결
5. 사이클 N+1로

종료: Recall ≥ 0.8 AND LOO 전원 상위 30%
      OR 5사이클
      OR 2사이클 연속 Recall 변화 < 0.05 (정체)

보고:
- 사이클별 점수 추이 표 (Recall, 평균 랭크, weights diff)
- weights.yaml 최종안 + 변경 근거
- LOO 결과 매트릭스
- 정체 시: "데이터 보강이 필요한 노드 목록" + "현 데이터로의 성능 한계 분석"
```

### P-5: L5 데이터 품질 루프

```
L5 데이터 품질 루프를 실행해줘.

사이클 (최대 3회):
1. 전체 엣지에서 20개 무작위 샘플링 (이전 사이클 샘플과 비중복)
2. 각 엣지의 evidence를 원문(seed/*.md)에서 대조:
   - [정상] 주장과 출처 일치
   - [출처소실] evidence URL/문서가 존재하지 않음
   - [과장] 출처는 있으나 주장이 원문보다 강한 표현
   - [오추출] 출처의 맥락과 엣지의 관계가 불일치
   - [날짜경과] asof 기준 6개월 이상 경과
3. 불량 엣지: 수정 가능하면 수정, 불가하면 폐기
4. 불량률 = 불량수/20
5. **체계적 패턴 감지**: 같은 소스파일에서 같은 유형의 불량이 3건 이상
   → L1 프롬프트에 해당 규칙 추가 → 해당 파일 재추출 (L1 연동)
6. 불량률 < 10%이면 종료, 아니면 다음 사이클

보고:
- 사이클별 불량률 + 유형 분포
- 수정/폐기 내역
- 체계적 패턴이 있었다면: 어떤 패턴이고 L1에 어떤 규칙을 추가했는지
```

### P-6: L6 강건성 루프

```
L6 강건성(민감도) 루프를 실행해줘.

사이클 (최대 3회):
```

## 실행 순서

```
P-0 (Phase 0 + L0) → P-1 (L1 추출) → P-2 (L2 커버리지) → P-3 (L3 무결성)
     │                                                          │
     └────── Phase 0-1 완료 ────────────────────────────────────┘
                                                                │
P-4 (Phase 2 + L4 캘리브) → P-5 (L5 품질) → P-6 (L6 강건성)
     │                                          │
     └────── Phase 2 완료 ──────────────────────┘
                                                │
P-7 (Phase 3 + L7 QA) → 최종 완료
```

각 프롬프트는 **이전 프롬프트의 산출물이 존재하는 상태에서 실행**하는 것을 전제.
루프 간 역류(L5→L1 등)가 발생하면 해당 프롬프트가 자동으로 지시.
